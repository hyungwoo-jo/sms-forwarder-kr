# WORKS → Webhook 최소판 계획

작성일: 2026-09-28. 기준 릴리스: `v3.5.0.260927-kr-7361b76`, 공통 versionCode `300061`.

## 목표와 배포 조건

- WORKS 알림에서 제목과 본문을 읽어 사용자가 지정한 HTTPS Webhook으로 전달한다.
- 기본 앱 화면에는 알림 접근, WORKS 규칙, Webhook 설정, 전송 기록과 연결 상태만 둔다.
- 기존 `com.hwserve.smsforwarder` 앱 ID와 개인 서명을 유지하고 versionCode를 `300061`보다 높여 데이터 삭제 없는 업데이트로 배포한다.
- 이전 기능의 코드는 Git 이력에 남긴다. 새 APK에서는 필요 없는 기능과 권한이 실제로 빠졌는지 병합 manifest와 DEX를 확인한다.
- 토스 허용 여부는 실제 기기에서만 확인할 수 있다. 허용을 보장하거나 탐지 회피를 목표로 하지 않는다.

## 1. 기존 설정과 흐름 확인

1. 현재 DB의 Rule/Sender 구조와 마이그레이션을 읽는다. 이미 저장된 WORKS 앱 규칙과 Webhook 설정을 업데이트 후 재사용할 수 있는지 확인한다.
2. 기기에서 읽을 수 있으면 현재 APK의 설정을 암호화 백업한다. 신규 빌드가 기존 백업·DB를 읽지 못해도 앱 시작이 실패하지 않도록 마이그레이션을 만든다.
3. 현재 Webhook 수신 서버의 실제 요청 형식과 필드 이름을 확인한다. 해당 계약을 유지하거나 서버와 동시에 변경한다. URL과 비밀키는 문서·테스트 출력에 적지 않는다.

## 2. 수집 경로 축소

1. `NotificationService`에서 WORKS 패키지만 처리한다. 패키지명은 기존 규칙의 값에서 확인하며 코드에 추측해 하드코딩하지 않는다.
2. `Notification.EXTRA_TITLE`, `EXTRA_TEXT`, `EXTRA_BIG_TEXT`를 이용한다. 본문이 비었거나 동일 알림의 중복 게시이면 한 번만 전송한다. 알림 자동 삭제 기능은 제거한다.
3. WORKS의 동일 대화가 알림을 갱신하거나 묶음 알림을 보낼 때 이벤트 식별자를 기준으로 중복 전송을 억제한다. 실제 기기에서 개별·묶음·수정 알림을 확인한다.
4. 전체 앱 목록 조회와 앱 선택 UI는 없앤다. 기존 WORKS 패키지 규칙을 마이그레이션하거나, WORKS 알림을 한 번 받은 뒤 그 패키지를 화면에 표시한다.

## 3. 출력 형식과 Webhook

1. 기본 본문은 `제목\n내용`만 사용한다. 빈 제목은 생략하고, 앱명·SIM·UID·기기명·시각·버전 같은 메타데이터는 붙이지 않는다.
2. HTTP 요청은 기존 Webhook 계약을 따르되 필요한 `source`, `title`, `text`, `event_id` 정도만 전송한다. 서버가 원문을 요약해 Telegram으로 보내는 현행 흐름이 있다면 서버가 한 번만 보내게 한다.
3. 요청은 HTTPS, 리다이렉트 차단, 비밀 URL/헤더 로그 마스킹을 유지한다. 실패 시 한국어 로그와 재시도 상태를 제공한다. 민감한 본문은 디버그 로그에 남기지 않는다.
4. 직접 Telegram 송신 기능은 새 APK에서 제외한다. 중복 알림 방지를 위해 기존 앱에 저장된 Telegram Sender가 실행되지 않도록 처리한다.

## 4. 권한·코드·화면 최소화

1. Manifest에서 SMS/MMS 읽기·수신·발신, 통화·연락처·전화 상태, `QUERY_ALL_PACKAGES`와 `GET_INSTALLED_APPS`, 원격 서버/클라이언트 관련 선언을 제거한다.
2. SMS 원격 명령, HTTP 서버, 통화·문자·자동 작업·위치·Bluetooth·FRP 등과 관련된 실행 경로와 의존성을 제거한다. 남는 코드의 참조를 컴파일로 확인한다.
3. 알림 접근, 네트워크, 전송 상태를 표시하는 데 필요한 권한만 남긴다. 부팅 복원·foreground service·절전 예외는 실제 전달 안정성에 필요한지 각각 검증해 최소 범위로 둔다.
4. 사용자에게 WORKS 알림 본문이 지정한 Webhook으로 전송된다는 사실과 앱 알림 접근 범위를 분명히 보여준다.

## 5. 검증과 릴리스

1. 순수 텍스트 렌더링, 알림 중복 억제, WORKS 이외 패키지 무시, 기존 DB 설정 이관, Webhook 요청 형식에 대한 테스트를 추가한다.
2. debug/release 빌드·테스트·lint·현지화 검사를 통과시킨다. 최종 APK의 권한·서비스·DEX·서명·앱 ID·versionCode를 이전 릴리스와 비교한다.
3. 같은 서명으로 기존 설치본 위에 업데이트되는지 실제 기기에서 확인한다. 설정과 로그 보존, WORKS 단일 알림 전달, Webhook 장애 후 재전송, 재부팅 후 수신을 점검한다.
4. 토스 실행 결과를 관찰한다. 계속 차단되면 그 경고 원문과 Play Protect 판정을 따로 기록하고, 토스에 오탐 검토를 요청한다. 이 결과를 확인한 뒤 새 공개 릴리스를 배포한다.

## 워치와 폰의 중복 알림

- WORKS 알림 자체가 워치에 전달된다면 Telegram 알림을 만들 필요가 없다. 앱은 Webhook만 보내고, 워치는 Galaxy Wearable/Wear OS에서 WORKS 알림을 받도록 설정한다. 서버가 Telegram 요약을 다시 보내고 있다면 해당 WORKS 경로의 Telegram 송신을 중지해야 폰의 두 번째 알림이 사라진다.
- 요약 Telegram이 꼭 필요하면 원본 WORKS와 Telegram은 폰에서 서로 다른 두 알림으로 남는다. Galaxy Watch의 `휴대전화에서 알림 음소거` 또는 Wear OS의 `Silence phone while wearing watch`는 폰 소리·진동을 줄이지만 알림 카드 두 개를 하나로 합치지는 않는다.
- 워치에서 WORKS만 받을지, 서버 Telegram 요약만 받을지 하나의 최종 경로를 정해 앱별 워치 알림을 조정한다. Telegram을 폰에서 완전히 차단하면 워치에도 전달되지 않을 수 있으므로 기기에서 확인한다.
